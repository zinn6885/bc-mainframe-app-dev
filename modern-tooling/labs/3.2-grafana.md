# Lab 3.2 – Grafana Observability Stack

**Duration:** ~90 minutes  
**Prerequisites:** AWS account with permissions to create IAM users, EC2 instances, S3 buckets, and security groups. Bitbucket account. Git installed locally.

## Learning Objectives

By the end of this lab you will be able to:
- Provision an EC2 instance using Terraform with a remote S3 state backend
- Trigger infrastructure deployments through a Bitbucket Pipeline
- Install Docker and Docker Compose on a Linux server
- Deploy a full observability stack using Docker Compose
- Use Grafana to explore logs, metrics, and distributed traces from a live application

---

## Overview

This lab provisions a cloud server, deploys a containerized observability stack on it, and uses Grafana to explore real telemetry data. The stack includes Loki for logs, Prometheus for metrics, and Tempo for traces. A FastAPI application instrumented with OpenTelemetry generates traffic across all three signals.

The infrastructure is defined in Terraform and deployed through a Bitbucket Pipeline so you can see how real teams provision environments through code rather than clicking through the AWS console.

> **Cost note:** A t3.medium instance in us-east-1 costs approximately $0.04 per hour. Remember to destroy the instance after completing the lab using the destroy pipeline.

---

## Hands On

### Part 1 – Create an S3 Bucket for Terraform State

Terraform stores a record of what it has deployed in a state file. Using S3 as the backend keeps the state in a shared location so the pipeline can read and update it on every run.

1. Log in to the **AWS Console** and navigate to **S3**.

2. Click **Create bucket**. Give it a globally unique name such as `terraform-state-grafana-lab-<yourname>`. Keep the region as **us-east-1**. Leave all other settings as default and click **Create bucket**.

3. Note the exact bucket name. You will add it to the Terraform configuration in the next step.

---

### Part 2 – Create an EC2 Key Pair

The key pair allows you to SSH into the instance after Terraform creates it.

4. In the AWS Console, navigate to **EC2 > Key Pairs** (under Network & Security in the left sidebar).

5. Click **Create key pair**. Give it a name such as `grafana-lab-key`. Select **RSA** and **.pem** format. Click **Create key pair**. The browser will automatically download the `.pem` file.

6. Move the `.pem` file somewhere you will not lose it, and restrict its permissions:

   ```bash
   chmod 400 grafana-lab-key.pem
   ```

7. Note the key pair name you used. You will need it when configuring the pipeline variable.

---

### Part 3 – Configure the Terraform Files

The Terraform files for this lab are in `terraform/` in the course repository. You will create a new Bitbucket repository for this lab, copy the files in, update the backend, and push.

8. In Bitbucket, create a new repository named `grafana-lab-<yourname>` inside the **Monitoring** project. Keep the default branch as `main` and include a README.

9. Clone the new repository to your local machine. Inside it, create a folder named `terraform` and copy `main.tf` into it from `labs/monitoring/terraform/`.

10. Open `main.tf` and replace `REPLACE-WITH-YOUR-BUCKET-NAME` in the backend block with the S3 bucket name you created in step 2:

    ```hcl
    backend "s3" {
      bucket = "terraform-state-grafana-lab-yourname"
      key    = "grafana-lab/terraform.tfstate"
      region = "us-east-1"
    }
    ```

11. Copy `bitbucket-pipelines.yml` from `labs/monitoring/terraform/` to the **root** of your new repository.

12. Commit and push all changes to the `main` branch.

---

### Part 4 – Configure AWS Access Keys

The pipeline needs AWS credentials to authenticate with AWS during `terraform init` and `terraform apply`.

> **If you already have an IAM user with programmatic access**, skip to step 14 and use your existing access keys, or generate a new access key for that user.

13. In the AWS Console, navigate to **IAM > Users**. Click **Create user**. Give it a name such as `grafana-lab-pipeline`. On the permissions page, attach the **AdministratorAccess** policy directly. For a production environment you would scope this down, but for a lab this is acceptable. Complete the user creation.

14. Open the user, click the **Security credentials** tab, and scroll to **Access keys**. Click **Create access key**. Select **Other** as the use case. Copy both the **Access Key ID** and **Secret Access Key**. You will not be able to retrieve the secret key again after closing this dialog.

15. In Bitbucket, open your repository and go to **Repository settings > Repository variables**. Add the following three variables. Mark the credential values as **Secured** so they are masked in pipeline logs:

    | Variable name | Value | Secured |
    |---|---|---|
    | `AWS_ACCESS_KEY_ID` | Your access key ID | No |
    | `AWS_SECRET_ACCESS_KEY` | Your secret access key | Yes |
    | `KEY_NAME` | Name of your EC2 key pair (e.g. `grafana-lab-key`) | No |

---

### Part 5 – Run the Pipeline

16. In Bitbucket, go to **Pipelines** in the left sidebar. Click **Run pipeline**.

17. Select the branch `main` and choose the custom pipeline named **deploy-grafana-lab**. Click **Run**.

18. Watch the pipeline steps execute: `terraform init` initializes the S3 backend and `terraform apply` provisions the security group and EC2 instance.

19. When the pipeline completes, scroll to the end of the output. Terraform prints the outputs defined in `outputs.tf`, including the public IP address and a ready-to-use SSH command. Copy the public IP.

---

### Part 6 – Install Docker and Docker Compose

20. SSH into the instance using the key pair you downloaded in Part 2:

    ```bash
    ssh -i grafana-lab-key.pem ec2-user@<public-ip>
    ```

21. Install Docker and enable it as a service:

    ```bash
    sudo dnf install docker -y
    sudo systemctl enable --now docker
    ```

22. Add your user to the `docker` group so you can run Docker commands without `sudo`:

    ```bash
    sudo usermod -aG docker $USER
    newgrp docker
    ```

    Verify Docker is working:

    ```bash
    docker run hello-world
    ```

23. Install Docker Compose using `wget` directly from the GitHub releases. The package manager version lags behind and can cause compatibility issues with some Compose files:

    ```bash
    wget https://github.com/docker/compose/releases/download/v2.29.2/docker-compose-linux-x86_64
    chmod +x docker-compose-linux-x86_64
    sudo mv docker-compose-linux-x86_64 /usr/local/bin/docker-compose
    ```

    Verify the installation:

    ```bash
    docker-compose --version
    ```

---

### Part 7 – Deploy the Observability Stack

24. Clone the LGTM compose repository:

    ```bash
    sudo dnf install git -y
    git clone https://github.com/d-blanco/grafana-lgtm-compose.git
    cd grafana-lgtm-compose
    ```

25. Create a `.env` file in the root of the cloned repository. The database passwords can be set to any value since this is a self-contained local stack:

    ```bash
    cat > .env << EOF
    MYSQL_ROOT_PASSWORD=rootpassword
    MYSQL_DATABASE=Crypto
    MYSQL_USER=user1
    MYSQL_PASSWORD=canbeanything
    DB_PASSWORD=canbeanything
    TEMPO_URL=tempo:4317
    EOF
    ```

26. Start the stack in detached mode:

    ```bash
    docker-compose up -d
    ```

    Docker pulls all required images and starts the containers. This may take a minute or two on first run. Check that all containers are running:

    ```bash
    docker-compose ps
    ```

    All services should show a status of `Up` or `running`.

---

### Part 8 – Generate Traffic

Before exploring Grafana, generate some application traffic so the stack has real data to display.

27. Open the FastAPI Swagger UI in your browser:

    ```
    http://<public-ip>:8080/docs
    ```

28. Use the Swagger UI to call several endpoints. Call them multiple times to create a meaningful volume of log entries, metrics, and traces. Each request generates telemetry across all three signals.

---

### Part 9 – Explore Grafana

29. Open Grafana in your browser:

    ```
    http://<public-ip>:3000
    ```

    Log in with username `admin` and password `admin`. Grafana will prompt you to change the password. You can skip this for a lab environment.

---

#### Explore Logs (Primary Focus)

Logs are the most direct signal for understanding what an application did and why something went wrong.

30. In the Grafana left sidebar, click the **Explore** icon (the compass). In the datasource dropdown at the top, select **Loki**.

31. Click **Label browser** and explore the available labels. Select the label for your application service to filter logs down to the FastAPI app.

32. Run a query and review the log stream. Click into individual log entries to expand them. Notice the structured fields Loki has parsed from each entry, including timestamp, log level, and any contextual fields the application included.

33. Filter the log stream to show only `error` or `warn` level entries. Identify whether any of your API calls produced errors and read the full log message to understand what happened.

34. Click **View in context** on any log entry. This shows the surrounding log lines in the same stream, giving you a before-and-after view of the event.

---

#### Explore Metrics

35. In the Explore datasource dropdown, switch to **Prometheus**.

36. Use the metrics browser to find metrics related to the FastAPI application. Look for request count, response time, or error rate metrics. Run a query and observe the resulting time series graph.

37. Try building a rate query over a short window to see requests per second across the time you were generating traffic.

---

#### Explore Traces

38. In the Explore datasource dropdown, switch to **Tempo**.

39. Search for traces from the FastAPI service. Open a trace to see the span waterfall. Each span represents one unit of work in the request path, showing how long each step took and in what order they executed.

40. Click into a span that shows a database call. Tempo captures the query details and timing, letting you see exactly how long the database interaction took within the overall request.

## Summary

In this lab you:
- Created an S3 bucket to store Terraform state and an EC2 key pair for SSH access
- Configured Terraform with a remote S3 backend and provisioned a t3.medium EC2 instance through a Bitbucket Pipeline
- Installed Docker and Docker Compose on the server via the command line
- Deployed a full LGTM observability stack using Docker Compose
- Used Grafana Explore to investigate logs, metrics, and traces from a live instrumented application

## Cleanup

To avoid ongoing AWS charges, destroy the instance when you are finished. In Bitbucket, run the **destroy-grafana-lab** custom pipeline. This runs `terraform destroy` and removes the EC2 instance and security group. The S3 bucket and IAM user you created manually are not managed by Terraform and should be deleted separately through the AWS Console.
