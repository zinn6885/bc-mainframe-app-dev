# Lab 3.3 – Infrastructure Drift Detection

**Duration:** ~20 minutes  
**Prerequisites:** Lab 3.2 completed, EC2 instance running, Bitbucket repository with Terraform files

## Learning Objectives

By the end of this lab you will be able to:
- Explain what infrastructure drift is and why it happens
- Detect drift using `terraform plan` in a Bitbucket Pipeline
- Resolve drift by updating Terraform code to reflect the actual infrastructure state

---

## Overview

Infrastructure drift occurs when the actual state of a cloud resource no longer matches what is defined in Terraform. This commonly happens when someone makes a manual change in the AWS console without updating the corresponding Terraform code. Over time, drift makes infrastructure unpredictable and breaks the reliability guarantee that infrastructure-as-code is supposed to provide.

In this lab you will intentionally cause drift by modifying the EC2 instance type through the AWS console, then use a Terraform plan pipeline to detect it, and fix it by updating the code.

---

## Hands On

### Part 1 – Cause Drift

1. In the AWS Console, navigate to **EC2 > Instances** and locate your `grafana-lab` instance.

2. Stop the instance. Select it, click **Instance state**, and choose **Stop instance**. Wait for the status to show **Stopped** before continuing.

3. With the instance selected, click **Actions > Instance settings > Change instance type**. Change the type from `t3.medium` to `t3.large`. Click **Apply**.

4. Start the instance again. Click **Instance state > Start instance**. Wait for it to reach **Running** status.

The instance is now `t3.large` in AWS, but your Terraform code still specifies `t3.medium`. This is drift.

---

### Part 2 – Add a Plan Pipeline

You need a pipeline that runs `terraform plan` without applying, so you can safely inspect what Terraform sees without making any changes.

5. In your repository, open `bitbucket-pipelines.yml` and add the following block inside the `custom` section, alongside the existing deploy and destroy pipelines:

   ```yaml
   plan-grafana-lab:
     - step:
         name: Terraform Plan
         script:
           - cd terraform
           - terraform init
           - terraform plan -var="key_name=$KEY_NAME"
   ```

6. Commit and push the change to `main`.

---

### Part 3 – Detect the Drift

7. In Bitbucket, go to **Pipelines** and click **Run pipeline**. Select `main` and choose the custom pipeline **plan-grafana-lab**. Click **Run**.

8. When the pipeline completes, read the plan output. Terraform compares the state file (which says `t3.medium`) against the live AWS resource (which is now `t3.large`) and reports a difference:

   ```
   ~ resource "aws_instance" "grafana_lab" {
       ~ instance_type = "t3.large" -> "t3.medium"
     }

   Plan: 0 to add, 1 to change, 0 to destroy.
   ```

   Terraform is proposing to revert the instance back to `t3.medium` because that is what the code says. This confirms drift has been detected.

---

### Part 4 – Fix the Drift

In this case, the larger instance size is intentional. The fix is to update the Terraform code to match the actual state, rather than reverting the infrastructure.

9. In your repository, open `terraform/variables.tf` and update the `instance_type` default value from `t3.medium` to `t3.large`:

   ```hcl
   variable "instance_type" {
     description = "EC2 instance type"
     type        = string
     default     = "t3.large"
   }
   ```

10. Commit and push the change to `main`.

11. Run the **plan-grafana-lab** pipeline again. The output should now show:

    ```
    No changes. Your infrastructure matches the configuration.
    ```

    The code and the actual infrastructure are back in sync. Drift is resolved.

---

## Summary

In this lab you:
- Caused infrastructure drift by manually changing an EC2 instance type in the AWS console
- Added a plan-only Bitbucket Pipeline to safely inspect drift without making changes
- Detected the drift in the Terraform plan output and understood what it means
- Resolved the drift by updating the Terraform code to match the actual infrastructure state

## Cleanup

Run the **destroy-grafana-lab** custom pipeline in Bitbucket. This removes the EC2 instance and security group. Once the pipeline completes, delete the S3 bucket and IAM user manually through the AWS Console, as those were not created by Terraform.

## Key Takeaway

Drift is a normal occurrence in real environments. What matters is having a process to detect and resolve it consistently. Running `terraform plan` regularly, or gating deployments behind a plan step, gives teams visibility into changes that happened outside of the normal code review process.
